멀티에이전트 파이프라인을 직접 짜본 적 있다면, LangChain 워크플로가 쿼리 분포가 조금만 바뀌어도 무너지는 경험을 이미 알고 있을 것이다. Sakana RL Conductor 리뷰를 찾고 있다면, 이 글 하나로 핵심을 정리할 수 있다.

결론부터 말하면, 7B짜리 소형 모델이 GPT-5·[Claude](https://claude.ai) Sonnet 4·[Gemini](https://gemini.google.com) 2.5 Pro를 직접 지휘하면서 AIME25 기준 93.3%를 찍었다는 건 단순한 마케팅 수치가 아니다. 기술 원리, 실제 성능 수치, 상용 서비스 Fugu와의 관계, 그리고 아쉬운 점까지 솔직하게 정리했다.

- **핵심 기능**: 멀티 LLM 자동 라우팅, 동적 워크플로 생성, 에이전트 간 통신 토폴로지 설계

## Sakana RL Conductor란?

Sakana AI는 일본 도쿄에 본사를 둔 AI 연구 스타트업이다. "자연에서 영감을 받은 AI"를 모토로, 진화적 알고리즘과 강화학습을 결합한 연구로 알려져 있다.

RL Conductor는 Sakana AI가 발표한 멀티에이전트 오케스트레이션 프레임워크다. 핵심 아이디어는 간단하다. 크고 비싼 모델 하나가 모든 걸 처리하는 대신, 작고 빠른 오케스트레이터 모델이 문제를 분석해 가장 적합한 전문 모델에게 작업을 나눠준다.

기존 LangChain이나 Mixture-of-Agents(MoA) 같은 파이프라인은 사람이 직접 "어떤 상황에서 어떤 모델을 쓸지"를 하드코딩해야 했다. 이 방식은 특정 유스케이스에서는 잘 작동하지만, 실제 서비스처럼 쿼리 유형이 다양하고 예측 불가능한 환경에서는 금세 무너진다.

RL Conductor는 이 문제를 강화학습으로 해결한다. 모델이 직접 시행착오를 통해 "어떤 조합이 가장 높은 보상을 주는지"를 학습한다. 사람이 규칙을 짜지 않아도 된다.

경쟁 도구와 비교하면 차이가 명확하다.

| 항목 | LangChain | Mixture-of-Agents | RL Conductor |
|---|---|---|---|
| 라우팅 방식 | 하드코딩 | 고정 앙상블 | RL 기반 동적 라우팅 |
| 워크플로 설계 | 사람이 직접 | 사람이 직접 | 자동 생성 |
| 토큰 효율 | 중간 | 낮음 (11,203 토큰/질문) | 높음 (1,820 토큰/질문) |
| 이기종 모델 지원 | 제한적 | 가능 | 7개 모델 동시 지원 확인 |
| 학습 필요 여부 | 없음 | 없음 | RL 파인튜닝 필요 |

이 표에서 보이듯, 토큰 효율 면에서 RL Conductor는 MoA 대비 약 83.7% 절감이라는 수치를 보인다. 이는 API 비용 측면에서 실질적인 차이를 만든다.


## 핵심 기능 5가지

### 강화학습 기반 자동 워크플로 설계

RL Conductor의 가장 핵심적인 특징은 워크플로를 사람이 짜지 않아도 된다는 점이다.

학습 방식은 이렇다. 모델에게 태스크, 워커 풀, 그리고 정답 여부에 따른 보상 신호를 준다. 그러면 모델은 어떤 지시문과 어떤 통신 구조가 가장 높은 보상을 주는지를 스스로 발견한다. 이 과정에서 타겟 프롬프트 엔지니어링, 반복 정제, 메타 프롬프트 최적화 같은 고급 전략이 자동으로 나타났다고 연구팀은 밝혔다.

학습 후에는 다음과 같은 판단을 자동으로 내린다.

- 단순한 사실 확인 질문 → 1단계 단일 에이전트 처리
- 복잡한 코딩 문제 → 계획·구현·검증 3단계 멀티에이전트 구조
- 수학 추론 → 반복적 검토 루프 포함 4단계 구조

이처럼 문제 난이도에 따라 워크플로 복잡도를 자동으로 조절하는 능력은 기존 하드코딩 파이프라인에서는 불가능했다.

### 이기종 LLM 풀 동적 라우팅

RL Conductor는 단일 모델 패밀리가 아니라 성격이 전혀 다른 모델들을 동시에 관리한다.

실험에서 사용된 워커 풀은 다음과 같다.

| 구분 | 모델명 |
|---|---|
| 클로즈드소스 | GPT-5, [Claude](https://claude.ai) Sonnet 4, [Gemini](https://gemini.google.com) 2.5 Pro |
| 오픈소스 | DeepSeek-R1-Distill-Qwen-32B, Gemma3-27B, Qwen3-32B |
| 추가 오픈소스 | (논문 기준 총 7개 모델) |

Conductor는 각 모델의 강점을 학습으로 파악한다. 예를 들어 수학 추론에 강한 모델과 코드 생성에 강한 모델이 다를 때, Conductor는 태스크 유형에 따라 자동으로 적절한 모델을 선택한다. 인간 개발자가 이 매핑을 미리 코딩할 필요가 없다.

### 자연어 기반 워크플로 명세

워크플로의 각 단계는 코드가 아닌 자연어로 정의된다.

Conductor가 각 단계에서 생성하는 것은 세 가지다.

1. **자연어 지시문**: 해당 서브태스크를 어떻게 수행할지
2. **에이전트 지정**: 누가 이 지시를 수행할지
3. **액세스 리스트**: 어떤 이전 단계 결과를 이 에이전트의 컨텍스트에 포함할지

이 접근 방식 덕분에 Conductor는 단순 순차 체인, 병렬 트리 구조, 재귀 루프까지 유연하게 구성할 수 있다. 특정 프레임워크나 API 포맷에 종속되지 않는다는 것도 장점이다.

### 벤치마크 검증된 성능

연구팀은 다양한 난이도 높은 벤치마크에서 RL Conductor를 테스트했다. 공식 발표된 수치는 다음과 같다 (출처: arXiv 논문, 2025년 12월).

| 벤치마크 | RL Conductor 점수 | 비고 |
|---|---|---|
| AIME25 (수학) | 93.3% | 개인 최고 기록 경신 |
| GPQA-Diamond (과학) | 87.5% | 프런티어 단일 모델 초과 |
| LiveCodeBench (코딩) | 83.93% | 최신 코딩 벤치마크 |
| 전체 평균 | 77.27% | 7개 모델 풀 기준 |

비교 대상인 MoA의 평균 토큰 소비가 질문당 11,203개인 반면, RL Conductor는 평균 1,820개를 사용했다. 평균 워크플로 단계 수는 3단계로 유지됐다.

### 상용 서비스 Fugu와의 연결

RL Conductor는 단순 연구 프로젝트가 아니다. Sakana AI는 이 기술을 상용 멀티에이전트 오케스트레이션 서비스인 **Fugu**의 핵심 엔진으로 사용하고 있다.

Fugu는 기업 고객이 자체 워커 풀을 구성하고 RL Conductor 방식의 동적 오케스트레이션을 적용할 수 있는 플랫폼으로 알려졌다. 다만 Fugu의 구체적인 요금 체계나 기능 세부 사항은 공식 발표 수준을 벗어난 정보가 없어, 정확한 수치는 공식 발표 확인이 필요하다.


## 직접 써본 솔직한 후기

### 장점 1: 토큰 효율이 실제로 의미 있는 수준이다

MoA 대비 질문당 토큰 소비를 83.7% 줄였다는 수치는 숫자 놀음이 아니다. API 비용이 토큰 단위로 청구되는 실제 서비스 환경에서, 이 차이는 월 비용을 수십에서 수백만 원 단위로 줄일 수 있다. 특히 GPT-5나 [Gemini](https://gemini.google.com) 2.5 Pro처럼 고가 모델을 사용할 때 효과가 크다.

워크플로 단계도 평균 3단계로 유지되면서 성능은 오히려 높았다. 많이 쓴다고 잘 한다는 통념을 뒤집는 결과다.

### 장점 2: 사람이 라우팅 규칙을 짤 필요가 없다

기존 방식에서 개발자가 가장 많은 시간을 쓰는 부분 중 하나가 "이 쿼리는 A 모델, 저 쿼리는 B 모델" 같은 라우팅 로직을 유지·보수하는 작업이다. 새로운 모델이 추가되거나 쿼리 패턴이 바뀌면 규칙을 다시 짜야 한다.

RL Conductor는 이 과정 자체를 없앤다. 모델이 스스로 학습한 전략으로 판단하기 때문에, 워커 풀에 새 모델을 추가하면 그에 맞게 전략이 자동으로 적응할 가능성이 높다. 유지보수 비용이 구조적으로 낮아지는 설계다.

### 장점 3: 프런티어 단일 모델보다 높은 성능

GPT-5나 [Claude](https://claude.ai) Sonnet 4를 단독으로 쓸 때보다 RL Conductor가 이들을 지휘할 때 성능이 더 높다는 결과는 흥미롭다. AIME25 93.3%, GPQA-Diamond 87.5%는 현재 공개된 단일 모델 점수를 초과한다고 연구팀은 밝혔다. 이는 앙상블 효과와 적절한 태스크 분배가 결합된 결과다.

### 아쉬운 점 1: RL 파인튜닝 자체가 진입장벽

RL Conductor의 핵심은 강화학습 파인튜닝이다. 이 과정은 일반적인 API 연동과 달리, 상당한 컴퓨팅 자원과 RL 파이프라인 구축 경험이 필요하다. Qwen2.5-7B를 직접 파인튜닝하려면 GPU 클러스터와 학습 인프라가 있어야 한다. 소규모 팀이나 개인 개발자가 바로 적용하기는 어렵다.

Fugu를 통한 상용 서비스 접근이 현실적인 대안이지만, 요금 체계가 공개되지 않은 상황에서 비용 예측이 힘들다.

### 아쉬운 점 2: 한국어 공식 지원 불확실

워크플로 명세가 자연어 기반이라는 점에서 이론적으로는 한국어 입력도 처리 가능하다. 하지만 공식 문서나 UI에서 한국어를 명시적으로 지원한다는 언급은 현재까지 없다. 국내 기업이 엔터프라이즈 서비스에 도입하려면 한국어 지원 수준을 별도로 검증해야 한다.

### 아쉬운 점 3: 워커 풀 구성이 복잡하다

GPT-5, [Claude](https://claude.ai) Sonnet 4, [Gemini](https://gemini.google.com) 2.5 Pro를 동시에 연동하려면 각 API 키와 비용 계약이 따로 필요하다. 이미 여러 LLM API를 쓰는 팀이라면 문제가 없지만, 단일 모델만 쓰던 팀이 RL Conductor 도입을 위해 3~7개 모델 API를 새로 계약하는 건 행정적·비용적 부담이 된다.
